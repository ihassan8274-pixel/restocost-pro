# 🧾 موديول التقارير — التصميم الكامل (RestoCost ERP)

**الإصدار**: 1.0 (مقترح تصميم — بدون تنفيذ)
**المبدأ الحاكم**: تجاهل كل التقارير المبنية (~30 شاشة مبعثرة). تصميم من الصفر لموديول واحد متكامل:
**مصدر بيانات ← محرك تجميع ← تعريف تقارير ← عرض/تصدير ← جدولة/توزيع**

---

## 1) الرؤية والأهداف

### 1.1 لماذا نعيد التصميم؟
النظام الحالي وصل إلى نقطة يملك فيها **أكثر من 30 شاشة تقرير** موزعة على 4 أقسام («التقارير والتحليل»، «منظومة التقارير المتطورة»، «التحليلات»، «الأتمتة»)، وكل شاشة:
- تعيد حساب نفس المفاهيم (الإيراد، تكلفة الطعام، الهامش) بطريقتها الخاصة → **أرقام متعارضة**.
- لا تشارك "لغة مشتركة" للفترة والفرع والتصنيف → لا يمكن مقارنة شاشتين على نفس الأساس.
- الجدولة والطباعة والتصدير (موجودة فعلاً في النظام) **غير مرتبطة** بمحرك حساب واحد.
- الحساب كله **في المتصفح (client-side)** بعد تنزيل نسخة كاملة من البيانات → كلما كبرت البيانات، بطؤت كل الشاشات.

### 1.2 الأهداف
1. **مصدر حقيقة واحد**: كل مقياس (إيراد، تكلفة، هامش…) له تعريف واحد في "قاموس المقاييس".
2. **واجهة واحدة**: شاشة تقرير واحدة تحل محل العشرات (بحث، مفضلة، فلاتر محفوظة).
3. **قابلية التوسع**: حسابات تُبنى مرة وتُخزَّن مؤقتًا (Cache) بدل إعادة حساب كل مرة.
4. **أتمتة**: أي تقرير قابل للجدولة والتوزيع (تيليجرام/بريد) بأزرار داخل التقرير نفسه.
5. **حوكمة**: كل رقم قابل للتتبع حتى سنده المصدر (Drill-down حتى مستوى الحركة/الفاتورة).

### 1.3 الشخصيات المستفيدة (Personas)
| الشخصية | احتياجه الأساسي من التقارير |
|---|---|
| المالك/الرئيس التنفيذي | P&L مجمع، مؤشرات سريعة (طعام/عمالة/هامش)، مقارنة فروع |
| مدير الفرع | إيراد وتكلفة فرعه يوميًا، جرد الفروقات، مراقبة المصروفات |
| المحاسب | قيود اليومية، ضريبة، ذمم، مطابقات GRN↔Journal، إقفال الشهر |
| مدير المشتريات | أفضل الأسعار، أداء الموردين، انحراف أوامر الشراء |
| مدير المطبخ المركزي | تكلفة إنتاج، هالك، إنتاجية الجزارة، التقيد بالوصفات |
| المدقق الداخلي | سجل التدقيق، التوزيعات، تحويلات الفروع، فروق الجرد |

## 2) مبادئ التصميم

1. **تعريف واحد لكل مقياس** — لا يوجد "إيراد" إلا تعريف واحد في القاموس.
2. **التقرير بيانات لا شاشة** — التقرير = تعريف JSON؛ العرض مجرد "مظهر" له.
3. **الحساب مرة، العرض ألف مرة** — التخزين المؤقت عند تغيّر البيانات (rev).
4. **كل رقم له سند** — Drill-down حتى المصدر (GRN، حركة، فاتورة، قيد).
5. **استغلال الجاهز** — نعيد استخدام: pdf.mjs، exceljs، jspdf، recharts، scheduled_reports، automation_rules، بوت تيليجرام، نموذج الصلاحيات، نظام الفروع/الشركات.
6. **الإقفال يحكم** — الشهر المغلق أرقامه ثابتة ومجمدّة؛ الأشهر المفتوحة تُحسب لحظيًا.
7. **فترة وأبعاد موحدة** — مكوّن فترة واحد وأبعاد (فرع/شركة/تصنيف/صنف/مورد) مشتركة في كل تقرير.

## 4) البنية المفاهيمية: التقرير = منتج بيانات

### 4.1 المخطط العام

```
┌──────────────────────────────────────────────────────────────────┐
│ ① طبقة الوصول الموحد Data Sources                                 │
│   محولات موحدة لكل مجموعة: batch_sales, grn, movements, journal…  │
└───────────────────────────┬──────────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│ ② محرك التجميع Aggregation Engine                                │
│   قاموس المقاييس + الفلاتر الموحدة + التجميع + النسب              │
│   + Cache على مستوى الفترة (rev-based)                          │
└───────────────────────────┬──────────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│ ③ سجل تعريفات التقارير Report Registry                           │
│   كل تقرير = JSON واحد (مصادر/أبعاد/مقاييس/رسوم/جدولة/صلاحية)    │
└───────────────────────────┬──────────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│ ④ طبقة العرض وواجهة واحدة                                        │
│   بطاقات KPI + جدول + رسوم + Drill-down + حفظ فلاتر + تصدير       │
└───────────────────────────┬──────────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│ ⑤ الجدولة والتوزيع                                               │
│   scheduled_reports + automation_rules + Telegram + بريد          │
└──────────────────────────────────────────────────────────────────┘
```

### 4.2 مثال تعريف تقرير (عقد موحد)

```jsonc
{
  "id": "food-cost-by-branch",
  "family": "cost",
  "nameAr": "تكلفة الطعام حسب الفرع: نظري مقابل فعلي",
  "purpose": "قياس انحراف الاستهلاك الفعلي عن النظري لكل فرع",
  "sources": ["batch_sales", "recipes", "daily_counts", "inventory_movements", "inventory", "grn"],
  "dimensions": ["branch", "period"],
  "metrics": [
    { "id": "revenue",         "labelAr": "الإيراد",                    "agg": "sum" },
    { "id": "theoreticalCost", "labelAr": "التكلفة النظرية",             "agg": "sum" },
    { "id": "actualCost",      "labelAr": "التكلفة الفعلية",             "agg": "sum" },
    { "id": "varianceAmount",  "labelAr": "فرق القيمة",                  "agg": "sum" },
    { "id": "foodCostPercent", "labelAr": "نسبة تكلفة الطعام",           "agg": "calc", "formula": "theoreticalCost / revenue * 100" },
    { "id": "variancePercent", "labelAr": "نسبة الانحراف",               "agg": "calc", "formula": "(actualCost - theoreticalCost) / theoreticalCost * 100" }
  ],
  "filters": ["period", "branch", "company"],
  "visuals": { "kpis": ["revenue", "foodCostPercent", "variancePercent"], "table": true, "chart": "bar", "heatmap": true },

  "permission": "reports:cost",

```

**قاعدة صارمة**: أي مقياس مركّب (نسبة، فرق) يُحسب **بعد** التجميع من المقاييس الأساسية، حتى لا تختلط النسب عند التجميع على مستوى أعلى.

## 5) قاموس المقاييس الموحد (مصدر الحقيقة الوحيد)

> كل مقياس مستخدم في أي تقرير يُعرَّف هنا مرة واحدة. أي "إيراد" في النظام = نفس الصيغة.

| المقياس | المعرف | الصيغة الموحدة | ملاحظات |
|---|---|---|---|
| الإيراد | `revenue` | Σ lineTotalRevenue من batch_sales (+ POS/توصيل عند التفعيل) − المرتجعات | يُخزَّن سعر وتكلفة لكل بند وقت البيع (snapshot) |
| الكمية المباعة | `qtySold` | Σ quantitySold | حسب الصنف/التصنيف/الفرع |
| التكلفة النظرية للطعام | `foodCostTheoretical` | Σ lineTotalCost من المبيعات (تكلفة بند فورية من BOM وقت البيع) | لا يعاد حسابها من BOM الحالي حتى لا تتغير الأرقام التاريخية |
| الاستهلاك الفعلي للطعام | `foodCostActual` | فتح رصيد + مشتريات (GRN) + وارد تحويلات − صادر − إغلاق (جرد) × التكلفة | لكل فرع/مادة خلال الفترة |
| فرق الاستهلاك | `variance` | الفعلي − النظري | موجب = استهلاك زائد (خسارة محتملة) |
| نسبة تكلفة الطعام | `foodCostPercent` | نظرية ÷ إيراد × 100 | المؤشر الحاكم للفروع |
| تكلفة العمالة | `laborCost` | Σ شفتات/رواتب الفترة (أساسي + أوفرتايم) | من payroll/shifts |
| نسبة العمالة | `laborPercent` | عمالة ÷ إيراد × 100 | |
| التكلفة الأولية Prime Cost | `primeCost` | طعام فعلي + عمالة | |
| نسبة Prime | `primePercent` | Prime ÷ إيراد × 100 | |
| مصاريف التشغيل | `opEx` | Σ operating_expenses للفترة (المستحقة، بغض النظر عن الدفع) | مع خيار "مدفوع فقط" |
| صافي الربح التشغيلي | `netOp` | إيراد − طعام فعلي − عمالة − مصاريف | قبل الاهلاك/الفوائد/الضريبة، قابل لإضافة الأقسام من خيارات |
| قيمة المخزون | `inventoryValue` | Σ رصيد × سعر التكلفة (معياري أو متوسط مرجح — خيار) | FIFO/متوسط عبر أداة التقييم |
| تغطية المخزون | `stockCoverDays` | رصيد ÷ متوسط الاستهلاك اليومي النظري | حسب تصنيف/فرع |
| ضريبة المشتريات | `vatIn` | Σ vatAmount من GRN | |
| ضريبة المبيعات | `vatOut` | Σ ضريبة المبيعات (من إعداد vat_inclusive) | |
| صافي الضريبة | `vatNet` | vatOut − vatIn | لدعم إقرار VAT |
| تقادم الذمم | `aging` | مستحق + أيام من تاريخ الفاتورة | شرائح: 0-30 / 31-60 / 61-90 / 90+ |

**قاعدة العملة**: كل المبالغ تُحسب وتُخزَّن بالعملة الأساسية (ريال). عند تفعيل العملات المتعددة يُحوَّل سعر الصرف عند **الإدخال** ويُحفظ الرقم الأساسي — التقارير لا تتأثر بأسعار الصرف اللاحقة.

## 6) الكتالوج الكامل للتقارير (8 عائلات × 24 تقريرًا)

> اسم التقرير مسبوق بمعرّف موحد. كل صف = تعريف تقرير واحد في السجل.

### 📈 العائلة أ: المبيعات والإيرادات `family: sales`

| المعرّف | التقرير | المصادر | الأبعاد | أبرز المقاييس | الشكل المقترح | الجدولة |
|---|---|---|---|---|---|---|
| `sales-daily` | الإيرادات اليومية | batch_sales | فرع، يوم | إيراد، كمية، متوسط سعر الفاتورة | جدول + خط زمني | يومي |
| `sales-monthly` | ملخص الشهر (فرع/تصنيف) | batch_sales | فرع، تصنيف، شهر | إيراد، % من الإجمالي | جدول + أعمدة | شهري |
| `sales-item-ranking` | ترتيب الأصناف | batch_sales | صنف، فرع | كمية، إيراد، هامش | جدول ترتيبي | شهري |
| `sales-comparison` | مقارنة الفترات PoP | batch_sales | فترة مقابل سابقة | نمو %، فرق | KPIs + خط | شهري مع مقارنة |
| `sales-menu-engineering` | مصفوفة هندسة القائمة | batch_sales + recipes | صنف | شعبية × هامش → نجوم/أبقار/ألغاز/كلاب | مصفوفة 2×2 | شهري |
| `sales-returns` | المرتجعات والاسترداد | pos_returns | فرع، صنف | قيمة مرتجع، هالك | جدول | شهري |
| `sales-channels` | قنوات البيع (داخلية/توصيل) | delivery_sales + batch_sales | قناة، فرع | إيراد قناة، عمولات | أعمدة | شهري |

### 🧮 العائلة ب: التكلفة والهوامش `family: cost` — **عائلة البرنامج الأساسية**

| المعرّد | التقرير | المصادر | الأبعاد | أبرز المقاييس | الشكل | الجدولة |
|---|---|---|---|---|---|---|
| `cost-theoretical-vs-actual` | **تكلفة الطعام: نظري × فعلي** | batch_sales + recipes + counts + movements | فرع، شهر | نظري، فعلي، فرق % | جدول + خريطة حرارية للانحراف | شهري |
| `cost-pot-vs-act` | الاستهلاك المتوقع POT × ACT | sales→recipes + جرد | صنف، فرع | كمية متوقعة × معدودة، فرق | جدول انحرافات | شهري |
| `cost-by-item` | تكلفة الهامش لكل صنف | batch_sales + recipes | صنف، تصنيف | تكلفة/حصة، هامش، سعر مقترح | جدول + أعمدة | شهري |
| `cost-category` | التكلفة حسب مجموعات المواد | recipes (بالمواد) | تصنيف مادة | تكلفة نظرية لكل مجموعة | أعمدة مكدسة | شهري |
| `cost-true` | التكلفة الحقيقية الكاملة (طعام + عمالة + تغليف + هالك + وجبات) | كل المصادر | فرع، صنف | Prime %، ربحية صافية | جدول + KPIs | شهري |
| `cost-trend` | اتجاه نسبة تكلفة الطعام (12 شهر) | النظري/الفعلي | شهر | % وتحركها | خط زمني | شهري |
| `cost-prime` | التكلفة الأولية والتشغيلية | sales + labor + opex | فرع | طعام/عمالة/تشغيل كنسب | أعمدة مكدسة | شهري |

### 🛒 العائلة ج: المشتريات والموردون `family: purchase`

| المعرّف | التقرير | المصادر | الأبعاد | أبرز المقاييس | الشكل | الجدولة |
|---|---|---|---|---|---|---|
| `purchase-monthly` | المشتريات الشهرية | grn + po | فرع، مورد، تصنيف | قيمة، كمية، عدد فواتير | جدول + أعمدة | شهري |
| `purchase-price-history` | **سجل أسعار الشراء** | grn | مادة، مورد | متوسط، آخر سعر، تذبذب %، أفضل مورد | خط عبر الزمن | شهري |

### 📦 العائلة د: المخزون والجرد `family: inventory`

| المعرّف | التقرير | المصادر | الأبعاد | أبرز المقاييس | الشكل | الجدولة |
|---|---|---|---|---|---|---|

## 7) التصميم المعماري (عقد الـ API والتخزين)

### 7.1 نقاط النهاية المقترحة

| الأسلوب | المسار | الوظيفة |
|---|---|---|
| GET | `/api/reports/meta` | قائمة العائلات والتعريفات + الصلاحيات المتاحة للمستخدم |
| GET | `/api/reports/run` | ?family=..&id=..&from=..&to=..&branch=all&company=..&compare=prev → `{ meta, kpis, rows, series, drill }` |
| GET | `/api/reports/drill` | ?path=branch:b-..&step=item → تفصيل المستوى التالي حتى الحركات |
| GET | `/api/reports/export` | ?family=..&id=..&format=excel|pdf → ملف جاهز للتنزيل |
| POST | `/api/reports/schedule` | ربط تقرير بتعريف جدولة (يومي/شهري + قنوات) — يكتب في scheduled_reports |
| GET | `/api/reports/summaries` | حالة المخزن المؤقت: آخر rev، آخر بناء، تغطية الفترات |

### 7.2 شكل الاستجابة الموحد

```jsonc
{
  "meta": { "reportId": "sales-monthly", "period": ["2026-09-01", "2026-09-30"],
            "comparePeriod": ["2026-08-01", "2026-08-31"], "branch": "all", "generatedAt": "…", "fromCache": true },
  "kpis": [ { "id": "revenue", "value": 123456, "delta": 0.12 },
            { "id": "foodCostPercent", "value": 34.2, "delta": -1.1, "direction": "down-is-good" } ],
  "rows": [ { "branchId": "b-..", "branchName": "الجبيل", "revenue": 12000, "foodCostPercent": 33.5, "…" } ],
  "series": [ { "label": "2026-09-01", "revenue": 4000, "cost": 1300 } ],
  "drill": { "nextSteps": ["category", "item", "movements"] }
}
```

### 7.3 التحقق والمصادقة
- كل النقاط تمر بنفس توكن الجلسة الحالي (sessionUser / readToken).
- الصلاحية تُفحص على مستوى العائلة قبل التنفيذ المباشر حتى لا يكشف الـ meta أي تقرير غير مسموح.
- تقارير الحوكمة والمالية مرتبطة بصلاحيات أعلى (view_accounting).

### 7.4 استراتيجية الأداء والتخزين المؤقت
1. عند كل تغيير بيانات (`rev change` — البنية موجودة عبر sync-state) تُعاد بناء **ملخصات الفترات** (يوم/شهر لكل فرع) لمجموعات المصادر الأساسية.
2. التخزين: مفاتيح KV جديدة ببادئة `rcerp_rpt_*` (مثل `rcerp_rpt_sales_day`, `rcerp_rpt_foodcost_month`) — نفس الآلية الحالية، قابلة للنسخ الاحتياطي.
3. تقرير يُفتح = قراءة ملخصات + تجميع خفيف (فلترة/ترتيب) → **هدف: فتح التقرير < 1 ثانية**.
4. التصدير الكبير يُنفَّذ في الخلفية (job) ويُسلَّم كملف جاهز عند اكتماله.
5. تقرير "عند الطلب" الثقيل (حركة المخزون) لا يُلخَّص مسبقًا؛ يُقرأ مباشرة بفلاتر مفهرسة (فرع × مادة × تاريخ).

### 7.5 أين يُحسب؟
| الخيار | الوصف | التوصية |
|---|---|---|
| **Server-side (الموصى به)** | محرك تجميع في store/routes — يخدم الواجهة والجدولة والبوت من نفس الكود | أساسي |
| Hybrid مرحلة أولى | حساب في الواجهة بنفس العقد JSON ثم نقل لاحق | مقبول كبداية أقل جهدًا |
| Client-only | الوضع الحالي — مرفوض | ✗ |

> القرار الفني لا يغيّر عقد العرض: الواجهة تستهلك `{meta, kpis, rows, series}` سواء حُسبت قرب المتصفح أم الخادم.

## 8) مواصفات واجهة المستخدم (شاشة واحدة)

### 8.1 الهيكل
```
┌────────────┬─────────────────────────────────────────────────────┐
│ الشريط     │ الشريط العلوي: اسم العائلة/التقرير + فترات + فلاتر   │
│ الجانبي    │ + أزرار: تصدير ▾ (Excel/PDF/طباعة) · جدولة · حفظ عرض │
│ ─────      ├─────────────────────────────────────────────────────┤
│ العائلات   │ بطاقات KPI (4–6) — صاعدة/هابطة بلون ذكي              │
│ بحث        ├─────────────────────────────────────────────────────┤
│ المفضلة    │ تبويبات: جدول | رسوم | تفصيل                        │
│ المجدولة   │ [الجدول: فرز، تجميع حسب البعد، تلوين حراري للنسب،    │
│ آخر ما     │  مجموع، عمود مقارنة الفترة السابقة]                  │
│ فتحته      │ [الرسوم: شريطي/خطي/مصفوفة 2×2 حسب التعريف]           │
└────────────┴─────────────────────────────────────────────────────┘
```

### 8.2 سلوكيات أساسية
- **الفترة**: مكوّن واحد (يوم/أسبوع/شهر/ربع/سنة/مخصص) + زر "قارن الفترة السابقة" + مفاتيح سريعة (هذا الشهر، الشهر الماضي).
- **الفلاتر الموحدة**: فرع (متعدد)، شركة، تصنيف، مورد — قابلة للحفظ كعرض مخصص باسم.
- **Drill-down**: نقرة على صف فرع → صفحة فرع (KPIs + أعلى أصنافه) → صنف → حركات/فواتير/قيود السندات.
- **حالة البيانات**: شارة "آخر تحديث: 15:30 (منذ دقيقتين)" و"محسوب من ملخص شهر مغلق" مقابل "تقديري لفترة مفتوحة".
- **فارغ بذكاء**: مجموعات فارغة (مثل التوصيل حاليًا) تظهر بحالة "لا توجد بيانات — يتفعّل عند استخدام الميزة" بدل جدول فارغ محيّر.
- **الاتجاهات** (`direction` في التعريف): down-is-good لعكس ألوان النسب التكلفة، up-is-good للإيراد — تلوين تلقائي.
- **طباعة**: وضع طباعة نظيف عبر `utils/print.ts` الحالي، مع ترويسة (شعار موجود rcerp_logo) وتذييل صفحات.

### 8.3 التصدير
| الصيغة | الأداة | المواصفة |
|---|---|---|
| Excel | exceljs (موجود) | ورقة "ملخص" (بيانات التقرير + الفلاتر + تاريخ الإنشاء) + ورقة "بيانات" (ترويسة مصفاة، إجماليات، تنسيق شرطي للنسب) |
| PDF | jspdf + autotable (موجود) | نموذج A4 عرضي للجداول، ترويسة الشركة، أرقام صفحات |
| طباعة | print.ts | HTML نظيف RTL بخط Cairo (الخط موجود في public/fonts) |

## 12) استراتيجية الاختبار وضمان الجودة

1. **مصفوفة تطابق مالية**: Σ GRN = Σ قيود journal (acc-inv + acc-vat) — تقرير فحص تلقائي في الاختبار وليس فقط عرضًا.
2. **بيانات ذهبية (Golden data)**: مجموعة بيانات ثابتة صغيرة (seed) تُحسب نتائجها يدويًا وتُقارن آليًا بعد كل تغيير (مثل `scripts/verify-unified.mjs` الحالي).
3. **اختبار الصيغ** لكل مقياس في القاموس: حالات حدية (صفر مبيعات، فترة بلا مشتريات، فرع جديد) في `server/test/*.test.mjs` (بنية node:test موجودة).
4. **اختبار التوافق**: نفس التقرير يحسب على الـ server وعلى الـ client (خلال المرحلة الهجينة) ويجب أن يتطابق — هذا يثبت صحة النقل لاحقًا.
5. **اختبار واجهة**: فتح كل تقرير من الكتالوج مع كل أنواع الفلاتر — لا شاشة بيضاء، لا فراغات، تنسيق RTL سليم.

## 13) خارطة الطريق (بدون تنفيذ الآن — مخطط فقط)

### المرحلة P1 — الأساس (تقدير: 4–6 أسابيع)
- قاموس المقاييس + محرك التجميع (server-side أو هجين حسب القرار) + Cache.
- شاشة واحدة: العائلات، الفترة/الأبعاد، KPI + جدول + رسم أول، تصدير Excel/PDF، طباعة.
- **التقارير الأساسية الخمسة**:
  1. `sales-monthly` (الإيرادات الشهرية)
  2. `cost-theoretical-vs-actual` (تكلفة الطعام نظري × فعلي)
  3. `finance-pl` (P&L الفرع)
  4. `inventory-movement` (حركة المخزون)
  5. `purchase-monthly` (المشتريات الشهرية)
- **خرج المرحلة**: بديل عملي عن النظائر القديمة الأساسية + إخفاء نظائرها القديمة.

### المرحلة P2 — التوسع (تقدير: 4–5 أسابيع)
- بقية العائلات (موردين، جرد، عمالة، إنتاج، ضريبة، ذمم، حوكمة) → تغطية ~30 تقريرًا.
- مقارنة الفترات + Drill-down العميق + حفظ الفلاتر/المفضلة + الخريطة الحرارية.
- جدولة أهم 3 تقارير مع تيليجرام.

### المرحلة P3 — الاحتراف (اختياري)
- جدولة شاملة لكل التقرير + لوحة تنفيذية (CEO) من نفس المحرك + ملخصات ذكية (AI) فوق نفس العقد.
- إخفاء نهائي لكل الشاشات القديمة (~30) وقياس: 100% من التقارير من مدخل واحد.

### مؤشرات نجاح الموديول
1. مدخل واحد يغطي كل احتياج تقريري (بدل 30 شاشة).
2. نفس المقياس = نفس الرقم في أي تقرير (مصدر حقيقة واحد).
3. فتح أي تقرير < 1 ثانية بعد أول بناء للـ cache.
4. تقرير مجدول يُسلَّم تلقائيًا ويصل تيليجرام/بريد بدون تدخل.
5. كل رقم يصل بسنده حتى الحركة/الفاتورة/القيد.

## 15) القرارات المفتوحة المطلوبة من الإدارة
1. **مكان الحساب**: Server-side (موصى به) أم هجين مرحلة أولى؟ (الفرق في المجهود والسرعة)

| `revenue` | Σ(batch_sales.items.lineTotalRevenue) − Σ(pos_returns.amount) | `SELECT branchId, SUM(lineTotalRevenue) FROM batch_sales, json_each(batch_sales.items) WHERE date BETWEEN … GROUP BY branchId` |
| `foodCostTheoretical` | Σ(lineTotalCost) (تكلفة فورية من BOM وقت البيع) | `SUM(lineTotalCost)` من نفس query المبيعات |
| `foodCostActual` | (فتح + GRN + وارد تحويل − صادر) − (إغلاق) لكل مادة × تكلفته | مجمعة من `inventory_movements` المصفاة + `daily_counts.consumedValue` |
| `variance` | `foodCostActual − foodCostTheoretical` | يُحسب بعد التجميع |
| `variancePercent` | `(actual − theoretical) / theoretical × 100` | طبقًا على المجموع فقط |
| `foodCostPercent` | `theoretical / revenue × 100` | بعد التجميع |
| `laborCost` | Σ payroll.lines + Σ shifts (أساسي + أوفرتايم) | من payroll/shifts للفترة |
| `primeCost` | `foodCostActual + laborCost` | بعد التجميع |
| `netOp` | `revenue − foodCostActual − laborCost − opEx` | بعد التجميع (قبل اهلاك/فوائد/ضريبة) |
| `inventoryValue` | Σ(quantity × standardPrice) أو متوسط مرجح خيار | `inventory JOIN raw_materials ON rawMaterialId` |
| `stockCoverDays` | رصيد ÷ متوسط الاستهلاك النظري اليومي (90 يومًا) | `quantity / (Σ qtySold×recipeQty / 90)` |
| `vatNet` | `vatOut − vatIn` | grn.vatAmount مقابل ضريبة المبيعات من الإعداد |
| `aging` | مستحق + أيام من تاريخ الفاتورة في شرائح | `julianday('now') − julianday(invoiceDate)` |

**قاعدة صارمة (مكررة للتوضيح)**: النسب المركّبة تُحسب **بعد** التجميع من المقاييس الأساسية — لا تُجمَّع النسب. مثال: متوسط نسبة تكلفة الطعام للمجموع ≠ متوسط نسب الفروع، بل = مجموع التكلفة ÷ مجموع الإيراد.

## B4) تصميم التخزين المؤقت (Cache) وخط البناء

مفاتيح KV جديدة (نفس آلية النظام — قابلة للنسخ احتياطيًا):

**خط الأنابيب**:
1. عند تغيير أي مجموعة مصدر (`rev change` — موجود فعلاً عبر /api/sync-state) تُجدول إعادة بناء المفاتيح المتأثرة فقط (نوع الحركة الجديد يؤثر على foodcost/movement فقط).
2. البناء يتم في الخلفية (watcher.mjs/بوت مشابه) — لا يُحسب عند فتح التقرير أبدًا.
3. التقرير عند فتحه يقرأ ملخصات + يجمع خفيف (فلترة/ترتيب) — هدف < 1 ثانية.
4. «عند الطلب» الثقيل (حركة المخزون/التدقيق) لا يُلخَّص — قراءة مباشرة مفهرسة.
5. تقرير فترة **مغلقة** يُقرأ من pl_summaries المجمدة ولا يتأثر بأي تحديث لاحق.

## D2) الحل: محرك طباعة موحد (Unified Print Engine)

### D2.1 المكوّنات — مبدأ "تنسيق واحد لكل شيء"
```
عقد الاستجابة (meta + kpis + rows + series)     ← من محرك التجميع (الجزء B)
                      │
                      ▼
        Print Spec (مواصفة الطباعة لكل تقرير)
        ترويسة · أعمدة · تذييل · اتجاه صفحات · شارة حالة
                      │
        ┌─────────────┼──────────────┐
        ▼             ▼              ▼
   طباعة متصفح   jsPDF (PDF)    exceljs (Excel)   ← نفس الـ Spec حرفيًا
   (HTML/CSS)    (نفس القالب)    (نفس الأعمدة)
```

**القاعدة الحاكمة**: لا يوجد "كود طباعة" داخل أي شاشة بعد الآن — الشاشة تطلب `export(spec)` والمحرك يخرج ثلاث صيغ متطابقة التنسيق.

### D2.2 "دستور الطباعة" الموحد (Print Constitution)
| # | القاعدة |
|---|---|
| 1 | RTL دائمًا بخط Cairo (موجود: `public/fonts/cairo.ttf`) — لا استثناءات |
| 2 | الترويسة: شعار (rcerp_logo إن وجد) + اسم الشركة + اسم التقرير + الفترة + تصنيف "سري/داخلي" |
| 3 | الجدول: ترويسة ملونة موحدة، مجموع سفلي، أرقام بفواصل الآلاف، نسب بصيغة `%`، عملة موحدة (ر.س) |
| 4 | التذييل: تاريخ الطباعة + اسم المستخدم الطابع + "صفحة X من Y" |
| 5 | شارة الحالة أعلى التقرير: `مُقفَل ✔` / `تقديري ⚠` / `بيانات ناقصة` (من meta.closed) |
| 6 | قياس ثابت: ورقة A4 — عرضية للجداول، طولية للبطاقات التنفيذية |
| 7 | الهوامش موحدة (20 مم) وأرقام الصفحات متسلسلة داخل الحزمة الواحدة |
| 8 | لا أصفار مضللة: القيم الفارغة = «—»؛ الصفوف ناقصة البيانات = شارة بجانبها |

## D3) حزم المستندات (Document Bundles) — "كتاب التقارير"

بدل أن «تطبع أكثر من تقرير بتنسيقات مختلفة»، تختار عدة تقارير + فترة واحدة فيُنتج **كتاب واحد موحد**:

```
كتاب الإقفال الشهري — سبتمبر 2026
  صفحة 1  غلاف (شعار + شركة + فترة + محرر)
  صفحة 2  فهرس المحتويات
  صفحة 3  ملخص تنفيذي (بطاقات KPI مجمعة)
  صفحة 4-5  إيرادات الفروع (sales-monthly)
  صفحة 6-7  تكلفة الطعام نظري × فعلي (cost-theoretical-vs-actual)
  صفحة 8-9  P&L الفروع (finance-pl)
  صفحة 10-11 المشتريات حسب المورد (purchase-monthly)
  صفحة 12-13 ضريبة القيمة المضافة (finance-vat)
  صفحة 14  توقيعات المديرين
```

- أرقام الصفحات **متسلسلة عبر الكتاب**، تنسيق موحد لكل التقارير، تذييل واحد.
- قوالب حزم جاهزة: «الإقفال الشهري» · «اجتماع الفروع» · «تقرير المالك» — قابلة للتخصيص.

### D4.2 "معادلة التكرار" (أثر الحل)
| المؤشر | الحالي | بعد الموديول |
|---|---:|---:|
| شاشات تقارير قابلة للفتح | ~30 | **1** (الموديول) |

| تعريفات المقياس (إيراد/تكلفة…) | متعددة متعارضة | قاموس واحد (§5) |

### D4.3 ضمان «رقم واحد، تنسيق واحد»
1. **لا طباعة خارج المحرك الموحد** — أي شاشة قديمة أثناء المرحلة الانتقالية تُمرَّر عبر `export(spec)` نفسه بدل كودها الخاص.
2. **لا حساب خارج القاموس** — أي عرض جديد يتم بالتجميع على المقاييس المرجعية فقط.
3. **مؤشر امتثال تلقائي** — سكربت تحقق (مثل verify-unified.mjs الحالي) يقارن: نفس التقرير من الشاشة القديمة والجديدة يجب أن يُطبعا بنفس التنسيق ونفس الأرقام.
